# 学习数据与首次加载修复记录

本轮按已确认的六个问题实施修复，保留既有查询预算、候选分页和后台统计优化。

## 实施方案

- 用户词文件保存代次标记；设置和引擎共用命名互斥量。保存只提交新增学习或撤销操作，旧代次的待保存操作不得跨越清空、导入边界。
- 文件以原子替换发布。宿主重新取得焦点、学习前及后台轮询检查数据身份；只有用户覆盖层发生变化，基础词库缓存继续复用。
- 搭配学习保存增量，成功后确认已写入部分；失败保留待保存状态并退避重试。模型和待保存集合均保持容量边界。
- 加载中订阅候选就绪刷新，并核对上下文及输入世代；空格和数字选择先补齐最新候选。
- 学习目录采用当前用户受保护 DACL，清理旧的宽权限。沙箱仅使用公共系统词库、系统快照、皮肤及必要设置，不直接读写个人学习数据。

## 部署与行为约定

用户词文件的两个标记分别管理词表和搭配代次。清空更新两个标记并删除搭配文件；
导入采用合并方式，只更新词表标记，因此已有搭配继续保留。旧的无标记三列、五列文件
可读取，保存后写入新协议。旧版 DLL 或设置程序不认识代次，升级时需要配套更新并关闭
仍使用旧 DLL 的宿主。

严格私有策略意味着 AppContainer 宿主只使用公共系统词库和资源，不提供个人学习、
自定义短语、置顶及统计。普通桌面宿主保留这些功能。安装器、设置程序与原生模块采用
一致的权限边界，安装或重新启动设置程序不会重新放开个人数据。

## 双核 CI 压力测试校准

首轮 GitHub 检查中，28 项测试通过，并发学习压力测试记录到 195 ms 的单次墙钟耗时。
本机限制为两个 CPU 核后也能复现。分段测量发现停顿散布于锁获取、文件属性查询和
调用计时边界；共享锁对照仍会触发，不能将该峰值直接归因于词典复制。

压力测试的四个读线程原先持续忙循环，会与被测线程争夺全部 CPU 时间。测试现改为
等待全部读线程完成首次查询，每轮查询后主动让出执行权，并在两次学习测量之间确认
查询继续推进。保留单次学习低于 100 ms 的上限，同时要求每轮至少有 20 次真实查询
与学习交错。引擎运行代码没有引入对照实验中的锁改动。

固定双核后的 30 轮独立进程复测全部通过，最高学习耗时为 31 ms，每轮最少完成
63 次并发查询，注册的 CTest 压力测试也通过。结果保存于
`artifacts/deploy-20260907/cooperative-stress.json`。
