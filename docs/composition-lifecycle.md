# 复制后重复输入与组合状态残留修复

用户报告复制一处文字后，在另一处输入时出现前文被重复拼接，并伴随黄色背景或组合高亮。
该现象涉及多个软件。排查重点是 TSF 组合的生命周期，而非仅修改绘制颜色。

## 已复现的状态错误

使用 Windows 提供的真实 TSF 文档、上下文和组合对象，向实际 `TextService` 派发受控通知：

- 旧组合结束通知未核对对象身份，会释放正在使用的新组合。继续输入后，同一上下文中出现
  两个活动组合，输入法内部状态与宿主不一致。
- 在只读编辑会话中切换焦点，同步清理无法取得写锁。原实现随后释放引用，宿主仍保留一个
  活动组合。测试允许消息队列继续运行后，该组合仍未结束。

基础 TSF 用例中正常结束组合会移除显示属性，因此修复针对残留的活动组合及错误回调，
没有通过强制设置背景色掩盖问题。不同宿主可为未结束的组合呈现不同高亮样式。

## 修复方式

- 结束通知先比较 COM 对象身份，只处理当前组合。
- 清理会话持有独立的旧组合引用。同步写会话被拒绝时，改为在原上下文排队执行，
  不通过成员指针触碰稍后创建的新组合。
- 记录最近一次成功写入的预编辑文本；延后清理仅在文本仍一致时删除预编辑内容，
  保留宿主已经改写的正文。敏感输入范围和密码控件不读取或改写正文。
- 最终文字写入成功、结束组合暂时失败时，只排队结束旧组合，避免重插或删除已上屏文字。
- 写入最终文字后，先清除组合显示属性，并将组合起点推进到末端，再结束组合。结束需要
  延后重试时，已上屏文字也已经退出活动组合范围，宿主不会在下一轮重新把它作为预编辑。
- 提交过程持有组合对象和候选副本，防止 COM 重入导致悬空引用。

## 回归覆盖

`composition_lifecycle` 验证迟到的旧通知、只读会话中的输入框切换、旧清理与新输入交错、
正文被宿主修改、最终提交后的结束失败与重试。测试检查实际文本和活动组合数量。
`tsf_e2e_core` 同时检查活跃组合的显示属性以及上屏后的属性清理。

第二轮补充检查结束失败当时的组合范围，而不只检查消息队列运行完后的最终状态。
原实现会在这个窗口内继续把已提交文字留在活动组合中；新增回归在修复前失败、修复后
通过。另按“教育 → 的 → 应用 → 前景 → 如何”逐次空格提交，检查每一步只追加本次文字。
显示属性检查逐个枚举属性范围，避免整段属性不一致时返回空值而漏掉局部残留。

## 复制后首段黄色标记

用户在第二轮本机测试中确认，逐段重复已经消失，但复制后首段文字的黄色背景要等下一个
字输入后才消失。截图中存在精确的 `RGB(255, 221, 85)` 像素，与 Blink 的默认组合背景
`#FFDD55` 一致。Blink 在收到空的组合样式段时使用该颜色，来源见
[默认组合颜色](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/layout/layout_theme.h)
及 [组合文字绘制入口](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/editing/ime/input_method_controller.cc)。

首键恢复原先调用 `ITfContextComposition::TakeOwnership`，但微软明确说明该接口
[尚未实现](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcontextcomposition-takeownership)。
原实现随后直接创建新组合，真实 TSF 回归复现了同一文字范围内的两个活动组合。
已有组合及其属性仍会参与宿主的显示状态计算，单独清理新组合不能完成这次接管。

修复只允许接管一个完全包含在已验证字母范围内的已有组合：先通过上下文组合服务结束它，
确认其确实消失，再复核上下文、文字和选区，最后创建唯一的新组合。范围超出目标、有多个
重叠组合或回调改变了目标时停止接管；不会调用“结束全部组合”，也不删除或重插正文。
组合起止位置调整后重新获取范围快照，用新的完整范围设置显示属性和光标。

宿主和输入法使用不同的编辑客户端及写锁。测试确认，不能在输入法写会话内直接终止宿主
组合；修复将终止操作排到原 TSF 线程的当前编辑会话之后，并在前后重新校验文字、选区
和输入世代，再申请新的输入法写会话。等待期间缓存后续字母与空格选词，光标移动或取消
后不会在过时位置补写。

回归使用不同的宿主和输入法客户端 ID，覆盖已有组合仅占字母尾部、完整显示属性覆盖、
上屏后属性清理，以及结束回调改写文字、移动光标、范围越界和交接前取消。接管测试在
修复前得到两个组合，修复后只有一个；立即连打并按空格的测试也检查上屏后没有活动组合。

首键恢复测试也使用 `TF_TMAE_NOACTIVATETIP` 和共用的按键派发适配器，避免已安装 DLL
与待测 DLL 同时订阅编辑通知、争抢掉落字母。复制、连续快打、清扫恢复、键盘粘贴和
鼠标粘贴五种场景继续检查原始首字母是否被完整恢复。

## 首字母候选窗消失与恢复任务丢失

候选窗首次绑定宿主或更换宿主时会重建 HWND。原来的 `WM_NCDESTROY` 处理同时清空了
排队的首键交接、完成通知和逻辑定时器，导致恢复停在一半，只能等待后续按键重新触发。
候选窗单独回归复现了两个排队动作及六种定时回调全部丢失。

受控的宿主重新绑定现在保留这些逻辑任务，在新 HWND 上按原顺序重新投递，并恢复轮询
和剩余延迟。真正关闭宿主、显式销毁候选窗时仍取消任务。新增集成回归把真实 TSF 首键
交接排入候选窗后立即重建窗口，验证无需再次按键也能完成恢复、继续组合并正确上屏。

测试使用隔离的用户目录和小词库；物理键盘路由由测试替代，不操作用户剪贴板，文档和
编辑会话仍来自 Windows TSF。此故障注入验证不能替代每个软件、网页编辑器的完整交互矩阵。

## 快速复制后，接管成功的首字母再次被宿主结束

2026-09-08 的本机诊断记录确认另一条真实路径。用户在 ima 中用 Ctrl+C 复制后约 1.46 秒
输入首字母；该字母没有经过输入法的按键回调，先由宿主写入正文。输入法在 08:46:53.324
开始恢复，下一毫秒完成接管。候选显示后，08:46:53.397 收到针对新组合本身的结束通知，
原实现随即清空候选。这 73 毫秒内没有焦点切换，恢复任务也没有丢失。

把复制到首键的间隔缩短至 565 毫秒后，电脑操控也复现了故障。硬件执行断点取得的调用栈
经匹配本机版本的微软符号解析，确认为 `textinputframework.dll` 中的
`CInputContextAdapter::DoEditSession → FinalizeComposition → _TerminateCompositionWithLock`
最终调用输入法的结束通知。不是候选窗口自行隐藏，也不是旧组合对象被误认成新对象。

恢复流程此前在 `TerminateComposition` 返回后立即申请新的异步写会话。TSF One 仍可能
有延后的宿主收尾工作，`TF_ES_ASYNC` 只协调编辑锁，不能当作宿主当前消息已经结束的
屏障。现在首次接管请求以及结束旧组合后的新写请求都通过原 TSF 线程的消息队列分阶段
执行，让宿主已经安排的收尾先运行。期间继续缓存字母和空格，并复核上下文、输入世代、
正文与选区；取消或切换输入框后不在过时位置补写。

回归用真实 TSF 文档与范围，配合提前授锁的适配层和延后宿主收尾，模拟已观察到的交错。
原写法得到 `new_terminations=1 active=0`，新写法得到 `new_terminations=0 active=1`。
原有正文完整性、连续空格上屏、重入及显示属性清理用例继续保留。同字重写的尝试没有
通过真实软件验收，已撤除，避免增加无效的正文改写。真实软件快速复制验收仍单独记录。

本机调试可在 CMake 中开启默认关闭的 `SHURU_INPUT_LIFECYCLE_TRACE`。它仅记录事件类型、
进程/线程及对象标识、状态和错误码，不记录按键字母、输入正文、候选或剪贴板内容。
该选项仅供短时诊断，常规构建保持关闭，避免给输入线程增加诊断写盘。
